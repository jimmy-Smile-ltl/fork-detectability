## 二、逐条说明：没采的维度是什么数据

### ⛔ D4 —— star 名单（**拿不到**）

| 项 | 内容 |
|---|---|
| 本来要采 | 哪些账号 star 了这个仓库（完整名单） |
| 端点 | `GET /repos/{o}/{r}/stargazers` |
| 实测结果 | 匿名 **401 Requires authentication**；带有效 token（非所有者）**404** |
| 结论 | **只有仓库所有者能读**，本项目匿名 → **永久放弃** |
| 替代 | 用 **fork 名单**（唯一可匿名获取的完整身份列表）|

### ⛔ D5 —— watch 名单（**拿不到**）

| 项 | 内容 |
|---|---|
| 本来要采 | 哪些账号 watch 了这个仓库 |
| 端点 | `GET /repos/{o}/{r}/subscribers` |
| 实测结果 | 匿名 **401**；非所有者 **404** |
| 结论 | 同 D4，**只有所有者能读** |

### ⛔ D12 —— 全站提交总数（**配额不可行**）

| 项 | 内容 |
|---|---|
| 本来要采 | 这个人在 GitHub **全站**的所有提交数 |
| 端点 | `GET /search/commits?q=author:{login}` |
| 限制 | 搜索 API **10 次/分钟**（匿名更少） |
| 结论 | 19.8 万人 × 1 次 = 需 **330 小时**，不可行 |
| 替代 | **D9**（在他自己的仓里数提交）+ **D13**（全年贡献日历） |

### 🔁 D3 —— 仓总数 + 最近 push（**被 D8H 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 公开仓总数、最近 push 时间 |
| 端点 | `GET /users/{login}/repos?per_page=1&sort=pushed` |
| 为什么不做 | **D8H 已经拿到完整仓库列表**（自建 vs fork、语言、更新时间），D3 是它的子集 |
| 省下 | 每人 1 次请求 × 19.8 万 = **19.8 万次** |

### 🔁 D7 —— 主页 HTML 的旧版设计（**被 D13 + D15 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 从主页 HTML 里抠贡献日历、成就、README |
| 为什么不做 | 拆成了两个更精确的单元：**D13**（专门抓 `/contributions` 页）+ **D15**（专门抓主页画像）|

### 🔁 D8 —— 仓库列表 API（**被 D8H 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 自建 vs fork 结构 |
| 端点 | `GET /users/{login}/repos?per_page=100&page=N` |
| 为什么初期用 HTML | 早期 API 配额被 star 采集吃满，HTML **0 API 配额** |
| 现在的状态 | BettaFish 已改回 **API `/repos`（62KB）**，因为 HTML 页面 223KB 在高并发下 0% 成功 |

### 🔲 D6 —— 组织列表（**可采未采，损失已评估**）

| 项 | 内容 |
|---|---|
| 本来要采 | 这个人属于哪些 GitHub Organization |
| 端点 | `GET /users/{login}/orgs` |
| 为什么没采 | 当初判断"组织归属"是弱判据（大厂员工才加 org），性价比低 |
| **实际损失** | D15 的 HTML 里其实**顺带解析出了 org**（`avatar-group-item`），但**写盘时漏了这个字段** |
| 补救成本 | 需重跑 D15（rea 10.8 万 + oc 8.2 万 ≈ 3 小时） |
| **对结论影响** | 无 —— 组织归属在已证伪的"档案类判据"里，两仓都不区分 |

### 🔲 D11 —— 单仓详情（**可采未采**）

| 项 | 内容 |
|---|---|
| 本来要采 | 每个仓库的 `parent` / `source` 关系、创建时间、fork 链 |
| 端点 | `GET /repos/{login}/{repo}` |
| 为什么没采 | 每人有多个仓，请求量 = 人数 × 仓数，**成本爆炸** |
| 实际损失 | 拿不到"fork 的 fork"这种二级传播链 |
| 对结论影响 | 低 —— 我们要判的是"账户是不是真人"，不是"fork 传播树" |

### 📦 D10 —— 粉丝/关注计数（**已含在 D1**）

`GET /users/{login}` 的响应里本来就有 `followers` 和 `following`，
不必单独请求。**省下每人 2 次请求 × 19.8 万 = 39.6 万次。**

### 📦 D2 的设计变更（90 天事件 → 30 条 RSS）

| 版本 | 端点 | 拿到什么 | 配额 |
|---|---|---|---|
| 原设计 | `/users/{login}/events/public`（1–3 页）| 近 **90 天**全部事件 | **1–3 次 API** |
| 实际采用 | `github.com/{login}.atom`（RSS）| 近 **30 条**事件 | **0 API** |

**取舍**：事件条数从"90 天全量"降到"30 条"，但**省下 1–3 次 API/人**（合计约 40 万次）。
`dev_event_ratio`（开发事件占比）用 30 条已足够稳定。

## 五、两个"列表"数据的完整度实测

> 用户最关心：**每人 star 过的仓 list** 与 **每人创建/fork 的仓 list**，是不是完整的？

### 5.1 star 过的仓库清单（D4L）

| 仓库 | 完整（拉完全部页） | 截断（卡在 100） | 完整样本的 star 数 | 截断样本 |
|---|---:|---:|---:|---:|
| rea | **81,711（82.1%）** | 17,842（17.9%） | 中位 7，最大 100 | 中位 **100**（上限） |
| openclaw | **61,553（81.4%）** | 14,069（18.6%） | 中位 6，最大 100 | 中位 **100** |
| **BettaFish** | — | — | — | ⚠️ **只有数量，没有 list** |

**判定规则**：`complete=1` 表示该账号的 star 总数 ≤ 100，**全部页都拉了**；
`complete=0` 表示总数 > 100，**只拉了前 100 条**。

**结论**：
- **82% 的账号，star list 是完整的**
- 剩下 18% 是**重度用户**（star 数 > 100），只截取了最近 100 条
- **BettaFish 例外**：新采集框架默认 `deep_star=False`，只取了 `/starred?per_page=1` 的**总数**，
  没有拉明细 —— 这是本轮的**已知缺口**

### 5.2 创建 / fork 的仓库清单（D8H）

| 仓库 | 完整 | 截断 | 仓总数中位 | 最大 | >100 仓的账号 |
|---|---:|---:|---:|---:|---:|
| rea | **88,379（81.9%）** | 19,549（18.1%） | 16 | 90 | **0** |
| openclaw | **65,961（80.9%）** | 15,583（19.1%） | 22 | 90 | **0** |
| BettaFish | 单页（API 100/页） | — | 30 | 100 | **0** |

**上限来源**：
- rea / openclaw：HTML 仓库页 **3 页 × 30 = 90** 个
- BettaFish：API `/users/{repos}?per_page=100` **1 页 = 100** 个

**结论**：
- **三仓都没有"仓数 > 100"的账号**（最大值 90 / 100）
- 所以**仓库清单对这个人群基本完整**，截断只发生在 90 个仓以上的少数人
- 每条记录都带 `own_details` / `fork_details`（各前 12 个的仓名、语言、更新时间）

### 5.3 这两个 list 能支撑什么判据

| 判据 | 依赖 | 截断是否影响 |
|---|---|:---:|
| `repo_named_target`（仓名含目标仓） | 自建仓清单 | ❌ 只看有没有，前 12 条足够 |
| `has_own` / `own_count` | 自建仓计数 | ❌ 计数来自页面统计，不是数数组 |
| `starred_target`（star 过目标仓） | star list | ⚠️ 重度用户可能漏判（目标仓在 100 条之外） |
| `star_fork_delay_h`（star→fork 延迟） | star list 时间戳 | ⚠️ 同上 |
| `fork_touched` | **fork 名单**（不依赖这两个 list） | ❌ 完全不受影响 |

### 5.4 补全成本（如果要 100% 完整）

| 缺口 | 数量 | 请求量 | 耗时 |
|---|---:|---:|---:|
| rea star list 未拉全（>100 星的人） | 17,842 人 | 约 5–10 页/人 ≈ 12 万 | ~4 小时 |
| openclaw star list 未拉全 | 14,069 人 | 同上 ≈ 9 万 | ~3 小时 |
| **BettaFish star list 完全没拉** | 7,465 人 | 约 1–5 页/人 ≈ 2 万 | **~1 小时** |
| 仓数 > 90 的账号补页 | **0 人** | — | 不需要 |

**建议**：补 BettaFish（成本最低、缺口最大），rea/openclaw 的重度用户不必补——
因为主要判据（`fork_touched`、`零粉丝`、`Pull Shark`）都不依赖 star list。

### 5.5 最终采纳的截断策略（2026-11-14 定稿）

**问题**：有极重度用户（如 `jyotidwi`，**star 了 10,610 个仓库**），
全量翻页要 107 页/人，且深层翻页会触发 GitHub 二级限流。

**实测分布**（已采 5,562 人的真实数据）：

| 分位 | star 数 |
|---|---:|
| p50 | **33** |
| p90 | 369 |
| p99 | **1,718** |
| p99.9 | 4,327 |

> **2.66% 的人（148 个）拥有 >1,000 star，却占了全部条目的 33.3%。**

**不同上限的代价**：

| 上限 | 保留数据 | 需翻页 | 省下的请求 |
|---:|---:|---:|---:|
| 100 | **31.5%** ❌ | 5,079 | 56.5% |
| 1,000 | 84.4% | 10,298 | 11.8% |
| **2,000** | **94.0%** ✅ | 11,139 | **4.6%** |
| 5,000 | 99.3% | 11,614 | 0.5% |

**定稿方案**：

| 项 | 设定 |
|---|---|
| 单人上限 | **20 页 = 2,000 条** |
| 真实总数 | **永远记录** `starred_total_est`（从 Link 头读） |
| 截断标记 | `complete=false` + `truncated=true`（**不伪装完整**） |
| 翻页间隔 | 前 5 页 0.15s，之后 **0.45s**（避开二级限流） |

**验证**（`jyotidwi`，10,610 star）：

```
items=2000  pages=20  complete=False  truncated=True  total_est=10700
```

**为什么这个上限对判据无损**：
GitHub 的 `/starred` **默认按点星时间倒序返回**（最新在前），
所以截断保留的是**最近的 star**，而 `starred_target` / `star_fork_delay_h`
这两个判据恰恰只依赖"最近的 star"。
**对判据而言，保留最近 2,000 条与全量等价。**

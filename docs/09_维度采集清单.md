## 二、逐条说明：没采的维度是什么数据

### ⛔ D4 —— star 名单（**拿不到**）

| 项 | 内容 |
|---|---|
| 本来要采 | 哪些账号 star 了这个仓库（完整名单） |
| 端点 | `GET /repos/{o}/{r}/stargazers` |
| 实测结果 | 匿名 **401 Requires authentication**；带有效 token（非所有者）**404** |
| 结论 | **只有仓库所有者能读**，本项目匿名 → **永久放弃** |
| 替代 | 用 **fork 名单**（唯一可匿名获取的完整身份列表）|

### ⛔ D5 —— watch 名单（**拿不到**）

| 项 | 内容 |
|---|---|
| 本来要采 | 哪些账号 watch 了这个仓库 |
| 端点 | `GET /repos/{o}/{r}/subscribers` |
| 实测结果 | 匿名 **401**；非所有者 **404** |
| 结论 | 同 D4，**只有所有者能读** |

### ⛔ D12 —— 全站提交总数（**配额不可行**）

| 项 | 内容 |
|---|---|
| 本来要采 | 这个人在 GitHub **全站**的所有提交数 |
| 端点 | `GET /search/commits?q=author:{login}` |
| 限制 | 搜索 API **10 次/分钟**（匿名更少） |
| 结论 | 19.8 万人 × 1 次 = 需 **330 小时**，不可行 |
| 替代 | **D9**（在他自己的仓里数提交）+ **D13**（全年贡献日历） |

### 🔁 D3 —— 仓总数 + 最近 push（**被 D8H 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 公开仓总数、最近 push 时间 |
| 端点 | `GET /users/{login}/repos?per_page=1&sort=pushed` |
| 为什么不做 | **D8H 已经拿到完整仓库列表**（自建 vs fork、语言、更新时间），D3 是它的子集 |
| 省下 | 每人 1 次请求 × 19.8 万 = **19.8 万次** |

### 🔁 D7 —— 主页 HTML 的旧版设计（**被 D13 + D15 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 从主页 HTML 里抠贡献日历、成就、README |
| 为什么不做 | 拆成了两个更精确的单元：**D13**（专门抓 `/contributions` 页）+ **D15**（专门抓主页画像）|

### 🔁 D8 —— 仓库列表 API（**被 D8H 替代**）

| 项 | 内容 |
|---|---|
| 本来要采 | 自建 vs fork 结构 |
| 端点 | `GET /users/{login}/repos?per_page=100&page=N` |
| 为什么初期用 HTML | 早期 API 配额被 star 采集吃满，HTML **0 API 配额** |
| 现在的状态 | BettaFish 已改回 **API `/repos`（62KB）**，因为 HTML 页面 223KB 在高并发下 0% 成功 |

### 🔲 D6 —— 组织列表（**可采未采，损失已评估**）

| 项 | 内容 |
|---|---|
| 本来要采 | 这个人属于哪些 GitHub Organization |
| 端点 | `GET /users/{login}/orgs` |
| 为什么没采 | 当初判断"组织归属"是弱判据（大厂员工才加 org），性价比低 |
| **实际损失** | D15 的 HTML 里其实**顺带解析出了 org**（`avatar-group-item`），但**写盘时漏了这个字段** |
| 补救成本 | 需重跑 D15（rea 10.8 万 + oc 8.2 万 ≈ 3 小时） |
| **对结论影响** | 无 —— 组织归属在已证伪的"档案类判据"里，两仓都不区分 |

### 🔲 D11 —— 单仓详情（**可采未采**）

| 项 | 内容 |
|---|---|
| 本来要采 | 每个仓库的 `parent` / `source` 关系、创建时间、fork 链 |
| 端点 | `GET /repos/{login}/{repo}` |
| 为什么没采 | 每人有多个仓，请求量 = 人数 × 仓数，**成本爆炸** |
| 实际损失 | 拿不到"fork 的 fork"这种二级传播链 |
| 对结论影响 | 低 —— 我们要判的是"账户是不是真人"，不是"fork 传播树" |

### 📦 D10 —— 粉丝/关注计数（**已含在 D1**）

`GET /users/{login}` 的响应里本来就有 `followers` 和 `following`，
不必单独请求。**省下每人 2 次请求 × 19.8 万 = 39.6 万次。**

### 📦 D2 的设计变更（90 天事件 → 30 条 RSS）

| 版本 | 端点 | 拿到什么 | 配额 |
|---|---|---|---|
| 原设计 | `/users/{login}/events/public`（1–3 页）| 近 **90 天**全部事件 | **1–3 次 API** |
| 实际采用 | `github.com/{login}.atom`（RSS）| 近 **30 条**事件 | **0 API** |

**取舍**：事件条数从"90 天全量"降到"30 条"，但**省下 1–3 次 API/人**（合计约 40 万次）。
`dev_event_ratio`（开发事件占比）用 30 条已足够稳定。

## 四、一句话总结

> **18 个设计单元 → 落地 8 个。**
>
> **拿不到的 3 个**（D4 star / D5 watch / D12 全站提交）是**接口权限或配额**的硬限制；
> **被替代的 3 个**（D3 / D7 / D8）是为了**省请求**；
> **可采未采的 3 个**（D6 / D11 / D2 全量版）是**性价比取舍**，
> 其中 **D6 组织归属是唯一"本可零成本拿到却漏存"的字段**。

## 〇、总原则：两轴五层，不求和

```
轴 1  身份自证 ── L1 档案层 / L2 生产层      「这个人有没有作为人存在过」
轴 2  批量性   ── L3 时间层 / L4 形态层      「这批动作是不是被统一指挥」
（新增）        ── L5 耦合层                  「动作之间的关系」
```

**禁止加权求和**：实测显示"爆发窗里的账号"（轴 2 异常）在轴 1 上**完全正常**，
合成一个分数必然把两类信息搅成浆糊。

## 三、L3 时间层：是不是被统一指挥

### 3.1 `fork_touched` fork 后动过（**零请求的宝贝**）

```python
# fork 名单的响应里本来就带 pushed_at
fork_touched = int(fork["pushed_at"] > fork["created_at"])
```

**必须做 fork 龄分桶**（两仓 fork 龄差 8 倍：30.6 vs 258.5 天）：

```python
if fork_age_days <= 30:  比较窗口 = "≤30 天"
elif fork_age_days <= 90: 窗口 = "31–90 天"
...
```

| 仓 | rea | openclaw | BettaFish | shardeum |
|---|---:|---:|---:|---:|
| 全量 | 8.4% | **33.5%** | 10.9% | 8.5% |
| **≤30 天窗口** | **6.4%** | **37.4%** | — | — |

**判定：✅ B 组仓库之间最强（−31pp）｜❌ 在A 组仓库上失效（shardeum 8.5% ≈ rea 8.4%）**

### 3.2 `burst` 爆发窗占比

```python
# 1) 把 fork 时间戳按小时分桶
dense[h] += 1
# 2) 滚动 3 小时求和
sums = [sum(dense[i:i+3]) for i in range(len(dense)-2)]
thr  = mean(sums) + 2*std(sums)
# 3) 落在超阈值窗口内的 fork 占比
burst = sum(1 for h in hours if flagged(h)) / len(hours)
```

| 仓 | rea | openclaw | BettaFish |
|---|---:|---:|---:|
| 爆发窗内 | **58.5%** | 40.3% | **54.4%** |

**判定：⚠️ 只能描述形态，不能当判据**（它本身就是分组依据 → 循环论证）

### 3.3 `collision` 同秒碰撞富集

```python
# 必须用**局部速率**，不能用全程平均
lam_local = 该小时内的 fork 数 / 3600          # 每秒期望
p_collide = lam_local**2 * exp(-lam_local) / 2  # 两两同秒的泊松期望
ratio = 实测同秒对数 / 期望同秒对数
```

| 仓 | rea | openclaw |
|---|---:|---:|
| 富集比 | **1.02×** | 0.95× |

**判定：❌ 证伪** —— 用全程平均算会得到 8.14×，用局部速率只有 1.02×（**这是本项目最经典的错误**）。

### 3.4 `BATCH` 注册批次聚集

```python
# 同一天注册的 forker 数 vs 泊松期望
expected = n * (1 - exp(-n/W))      # W = 观察窗口天数
BATCH = 实测同日注册对数 / expected
```

| 仓 | rea | openclaw |
|---|---:|---:|
| 富集比 | **0.9×** | **0.9×** |

**判定：❌ 证伪** —— 低于泊松期望，说明注册比我随机还分散。

## 八、一句话总结

> **账面上能看到的（档案、头像、命名、自建仓）几乎全部无效；
> 真正有效的是"产出了什么"（提交数）与"动作之间什么关系"（star→fork 时差）。**
>
> 而**最意外的发现**是：在已知A 组仓库 shardeum 上，
> 排名第一的 `fork_touched` 失效了（8.5% ≈ rea 的 8.4%），
> 反而是"提交数为 0"这条最朴素的判据最强。

### 9.3 关于 `fork_touched` 的措辞更正

**此前写**："`fork_touched` 在A 组仓库上失效（8.5% ≈ rea 的 8.4%）"
**更准确的说法**：

| 仓库 | `fork_touched` | 排序 |
|---|---:|---|
| **union(A 组)** | **6.6%** | 最低 |
| rea | 8.4% | — |
| **shardeum(A 组)** | 8.5% | — |
| BettaFish | 10.9% | — |
| openclaw | 33.5% | 最高 |

**两个A 组仓库确实是最低的两名**，但 **rea（8.4%）夹在中间**。

所以正确的表述是：

> **`fork_touched` 有方向性（A 组仓库最低），但区分度不足**
> （6.6% vs 8.4%，只差 1.8pp）——
> 它无法区分"造假"与"rea 这类资源型项目的受众"。

### 10.5 为什么 `fork_touched` 会彻底失败

| 仓库 | `fork_touched` | 类型 |
|---|---:|---|
| union(A 组) | 6.6% | 资源型（fork 当收藏） |
| rea | 8.4% | 资源型（历史地图） |
| shardeum(A 组) | 8.5% | 资源型 |
| BettaFish | 10.9% | 工具型（部署） |
| ollama净 | 25.6% | 工具型（定制） |
| openclaw | 33.5% | 工具型（深度定制） |
| langchain净 | 34.6% | 工具型 |
| **anoma(A 组)** | **73.5%** | ⚠️ **属 A 组但高度活跃** |

**它测的是"这个仓库的 fork 是拿来用还是拿来收藏"，与真假无关。**

anoma 的 73.5% 说明：**高成本操作服务用的是养了多年的老号，
这些号会真的 push、真的 commit** —— 只有"不写自己的代码"这一点露了馅。

### 10.6 最终的一句话

> **8 个仓库、25.3 万个 forker、218 万条记录之后，
> 能可靠区分"A 组仓库"与"B 组仓库"的判据只剩一条：
> 「有没有自建仓」——A 组仓库 forker 里约 40% 连一个自建仓都没有。**
>
> **而这条判据本身也不是"造假证据"，它是"受众画像"：
> 加密项目的 forker 本来就更少写代码。**

### 10.7 对原研究结论的影响

原结论：「rea 与 openclaw 之间没有造假证据」。

**这个结论不变，但理由更强了**：

| 原来的理由 | 现在的理由 |
|---|---|
| rea 的 21 个判据都被证伪 | **连"已知A 组仓库"的判据都只有 1 条能分离** |
| 爆发窗内外账号无差异 | 同上，且 anoma 证明"活跃"≠"真实" |

**换句话说：不是 rea 清白，而是"用 fork 侧公开数据判断造假"这件事本身，
能力极其有限。**

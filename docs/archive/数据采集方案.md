### C. fork 名单 —— 判"fork 质量"

| # | 数据 | 关键指标 | 状态 | 优先级 |
|---|------|---------|------|--------|
| C1 | 全量 fork 名单 | login / created_at / pushed_at / 是否有后续提交（fork_touched）/ size / 语言 | ✅ **已采全**（82,176 条 / 82,006 唯一 login；缺 409 条 = 已删 fork） | ★ |

> **C 组为什么能拿全 —— 结构性前提（2026-11-05 确认）**：fork 的可见性由上游决定，**fork 主人无法改成私有**
> （设置页报错「For security reasons, you cannot change the visibility of a fork.」；官方文档「You cannot
> change the visibility of a fork by itself.」）。上游转私有 → 公开 fork 留在**独立网络**继续公开；上游被删 →
> 活跃 fork **接任新 upstream**。**唯一消失方式是删除**，故 `forks_count` 与可列出条数的差额**只可能**是删除，
> 不存在「转成私有所以看不到」这条替代解释；漏采方向是**低估**（*Duplicate repository* 是独立仓库、不是 fork，
> 不进 `/forks`）。**fork 操作本身也是公开的**（`/forks` 名单 + forker 自己的仓库列表 + public events 的
> `ForkEvent`，三处可交叉验证）。⚠️ GitHub **搜索默认不返回 fork**（需 `fork:true` / `fork:only`），
> **名单一律以 `/forks` API 为准**，别把网页搜索结果当覆盖率口径。

### star/watch 名单通道死亡验证（2026-10-25/26 终审）
结论：**`/repos/{o}/{r}/stargazers` 与 `/subscribers` 自 2026-06-30 起仅 admin/collaborator 可见（GitHub changelog「Upcoming access restrictions to public API endpoints and UI views」），任何 token 均不可用**。验证矩阵（排除法，≤10 次请求）：

| 假设 | 验证 | 结果 |
|------|------|------|
| token 无效？ | `/user`（带 token） | 200，账号身份正常 |
| 账号被风控？ | `/users/{样本账号}` | 200，账号存活 |
| 仓库不存在/已删？ | `/repos/morluto/rea` | 200，388,242★ |
| 端点整体死？ | 同账号打其他端点 | 200 |
| **端点权限收紧？** | 带 token 打 `/stargazers` + `/subscribers` | **404 / 403** ← 唯一失败项 |

附：UI /stargazers 页全站 404（vscode/ollama 同死）；`/users/{username}/subscriptions` 已弃用。**GitHub 对无权限资源返回 404（而非 403）以隐藏资源存在性**——排查时别被 404 误导成"仓库没了"。

**对采集策略的含义**：不要再尝试任何 token 路线打名单端点（含样本账号 token——账号本体是批量注册小号，能不用就不用，何况通道已死）。身份级数据全部走 CH（样本内比例）+ `/users/{login}/starred`（逐人校准抽检）。

### 本机网络特殊性（影响所有 HTTP 代码）

- `api.github.com` 与 `dps.kdlapi.com` 均存在**按 TLS 指纹的连接重置**：python-requests 直连必死，curl_cffi 需在 profiles 间轮换 + 每指纹重试 2 次（实测抑制窗口有抖动，单次失败不代表该指纹死）。
- 结论已固化到 `_detail_probe.py::get()`：`PROFILES × 每指纹 2 次 + 间隔 1.5s`，全失败才抛错。

## 三、数据用途：信号 → 数据映射（2026-10-31 修订：三轮优化后）

每条"异常信号"都必须有对照组基线（第五节 E 组），否则只是猎巫。**2026-10-25 三轮优化（S1 扩对照 / S2 CH 作者归因 / S3 25 人实检）推翻了三个旧信号**，现表按存活状态重排——判别力降序：

### 3.1 存活信号（有判别力）

| 信号 | 计算 | 依赖数据 | 状态与基线 |
|------|------|---------|-----------|

## 五、合规性

1. **不登录**（用户指定，也是本项目最干净的边界）：无登录、无 cookie 参与；不碰用户大号环境令牌；不登录三个实证小号（只走公开 API）；无账号被封风险。**唯一例外已发生并关闭**：2026-10-25 用户批准用样本账号 token 做 `/stargazers` 通道一次性验证（≤10 次只读 GET），结论 = 通道死（见 §二）；样本账号本体是批量注册小号，**此后不再使用其任何凭据**（邮箱密码尤其不应使用）。
2. **只读公开数据**：全部端点为 GitHub 公开 API / 公开页面；不采私有数据、不绕权限（star 名单 admin-only 即接受，**不找破解路线**——token 验证只为确证通道状态，不为绕过）。
3. **限流纪律**：匿名 60/h 主动节流（1.2s+/req）；Search API 10/min 独立桶；尊重 Retry-After 与二次限流信号；断点续爬避免重复请求。
4. **代理例外的边界**：两次，均为用户决策并记录在案（README「请求配额与令牌」）：① 2026-10-24 fork 名单 822 页（KDL 私密代理，凭据在 gitignored `data/proxy_kdl.json`）；② 2026-10-31 forker 主页 D1 全量 82k（**本地 本机代理Verge 订阅节点池**，零新增凭据）。均匿名只读、不涉账号、**不扩展为项目默认**；后续再动用代理需用户重新决策。
5. **HTML 通道遵守 robots**：star-history.com robots 仅禁 `/embed`（已知）；github.com 爬取仅用单页探测不做批量抓取（HTML 不作为批量通道）。
6. **个人信息最小化**：公开 email/公司/地点只做**聚合统计与布尔特征**（"有/无公开联系方式"），不落具体值入报告；用户画像数据仅本地存储（gitignored），不外传；报告不点名个体账号定性"造假"（措辞 = 异常信号 / 真人几率）。
7. **ClickHouse**：playground 官方公开服务，免凭证使用即默认允许的匿名查询；一次性导出落盘，不依赖重放。
8. **明确禁止（重申）**：多账号池分摊配额（会牵连真实账号）、登录小号采数据、破解验证码/风控。

## 七、数据利用总览：一仓到手后跑什么（2026-10-31 新增）

前三节回答"数据从哪来"，本节回答"**每个数据怎么变成判据**"。给一个新仓库（如再遇到疑似刷量仓），按成本升序的操作流水线——**每一步都可能直接给出结论，不必跑完**：

### 7.1 第一层：两个免费请求定性（~4 req，分钟级）

| 步骤 | 端点 | 算什么 | 已知参照系 |
|------|------|--------|-----------|
| 1 | `/repos/{o}/{r}` | star/fork/watch/issue 总量 → **issue/千★** | rea 8.5 / BettaFish 10.4（可疑）vs openclaw 155 / ollama 62 / n8n 51（正常人群参与） |
| 2 | `/repos/{o}/{r}/stargazers/history`（分页） | 30 周曲线 → **单脉冲 or 持续**；99% star 是否集中在几天 | rea = 15 天脉冲后归零；openclaw = 11 个月不衰减；BettaFish = 单尖峰+平滑长尾 |

**判读**：issue/千★ < 15 且曲线单脉冲 → 直接送 CH 验身份（7.2）；两项都正常 → 大概率有机，收工。

### 7.2 第二层：CH 身份三板斧（3 条 SQL，免登录）

| 板斧 | SQL 形态 | 判什么 | 参照系 |
|------|---------|--------|--------|
| **行为宽度** | 对该仓 stargazer 群体：`SELECT countDistinct(repo_name) ... WHERE actor IN (...) AND created_at >= 窗口起点 GROUP BY actor` → 单-star 率 / p50 | 账号池性质（养号/小号只服务单一目标仓） | rea 42.8% 单-star vs ollama 15.1% / BettaFish 12.9%；**宽度窗必须与选样窗解耦**（统一 `2026-01-01` 起） |
| **同秒聚集** | WatchEvent 按秒分桶，秒内 ≥2 actor 占比，Poisson 校正 | 批量执行痕迹 | openclaw 富集 12–24×（vs react/linux 基线）；**dify/browser-use 基线待补** |
| **事件结构** | `event_type` 分布 + 去重 actor 数 | 开发侧 vs star 侧是否失衡 | rea：5,923 watcher vs **7 个** pusher；WatchEvent 几乎一人一 star |

**覆盖铁律**：先查该月覆盖（`count() / 官方周增量`），<5% 不出结论；只做样本内比例，不做绝对数。

### 7.3 第三层：API 抽人复核（30–50 req，小时级）

CH 圈出可疑子群（如单-star 账号）后，抽样逐人采：

- `/users/{login}` → 号龄/粉/仓（D1）——rea 单-star 池实测 = **老号+新号混合**（购买存量小号+新号的形态），不是清一色新号
- `/users/{login}/repos` → **fork vs 自建结构**（D8）：真人 = 自建仓有 push；批量号 = 全 fork 无自建/空壳自建
- `/users/{login}/starred?per_page=1` → Link 尾页 = 真实 star 总数，与 CH 宽度互证（CH 窗内 1 仓但 API 总数 500 = 活跃用户被窗口低估；API 也 0-1 = 真单-star 号）

### 7.4 第四层：生态位核查（收尾）

- 同 owner 名下仓列表（`/users/{o}/repos`）：多仓**同日创建 + 同期起飞** = 协同异常（storytold 5 仓 2026-09-30 同日建、10 月齐飞）
- 仓库转移史（旧 owner 名下 404 + CH 里有旧名事件）：clawdbot→openclaw、storytold/rea→morluto/rea
- 对照组永远同跑（§3.1 每行都有基线要求）——**没有基线的数字不出报告**

### 7.5 已验证的完整案例（本仓库 `data/out/`）

| 仓 | 走到的层 | 结论 |
|----|---------|------|
| rea | 7.1→7.4 全走 | **强异常**（issue/千★ 8.5 + 单脉冲 + 42.8% 单-star + 7 pusher + 家族协同 + 转移史）|
| BettaFish | 7.1→7.3 | 曲线异常但身份健康（p50 宽度 7 仓、12 人抽检真人结构）→ **初判有机爆红** |
| openclaw | 7.1→7.3 + 三轮优化 | 结构信号全线失效/反转（§3.2）；画像收敛为"一人+AI 作者驱动型"；**唯一未解释项 = star 增速本身**，待 S5/CH 身份级数据 |

> **一句话方法论**：曲线定形态（脉冲/持续），CH 定人群（宽度/同秒），API 定个人（号龄/自建仓），对照定异常——四层递进，每层都有已死信号的教训兜底（§3.2）。

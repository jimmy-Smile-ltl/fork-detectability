# 账户数据体系设计（完整字段与子字段）

> 目标：把"一个 GitHub 账户能采到什么、每个字段怎么用、值不值得采"一次说清，
> 并显式列出**当前采集浪费掉了哪些已经拿到手的数据**。
> 配套：[`账户采集方案.md`](账户采集方案.md)（端点级）、[`账户分析方案.md`](账户分析方案.md)（判据级）
> 原则：一次请求拿到的对象不要只用其中 3 个字段；能用 Link 头拿计数的，不要为计数多翻页。

---

## 1. 现状审计：拿到了什么、落盘了什么、扔了什么

| 端点 | 请求 | 响应里其实有什么 | 当前落盘 | **被丢弃** |
|---|---:|---|---|---|
| D1 `/users/{login}` | 1 | 30+ 字段（含 `avatar_url`、`gravatar_id`、`node_id`、`site_admin`、`user_view_type`） | 16 个字段 | `avatar_url`（可用 `user_id` 拼）、`gravatar_id`、`node_id` |
| D2 `/events/public` | 1–3 | 事件数组（含 repo、payload、时间） | 类型计数 + 首末时间 + 去重仓数 | **每个事件的仓库名/时间/类型明细** |
| D3 `/repos?per_page=1` | 1 | **1 个完整 repo 对象**（81 个字段） | 只用了 Link 尾页（=总数）+ 最近 push | 那个 repo 对象本身 |
| D4 `/starred?per_page=1` | 1 | **1 个完整 repo 对象** + Link 尾页 | 只用了 Link 尾页（=总数） | ⚠️ **star 的仓库列表完全没采** |
| D5 `/subscriptions` | 0 | 未使用 | — | ⚠️ watch 列表整个未采 |
| D6 `/orgs` | 1 | org 对象数组 | 仅 login 列表 | org 的 id/描述/主页 |
| D8 `/repos?per_page=100` | 1–3 | **每个仓 81 字段 × 最多 300 个** | 聚合 6 个 + 前 20 个自建仓的 5 个字段 | **fork 仓一个都没存**（只有计数）；自建仓只存前 20 个 |
| D9 `/commits?author=` | 0 | 未使用 | — | ⚠️ "自己的仓里有没有本人提交"未采 |
| D10 `/followers`·`/following` | 0 | 未使用 | 只有计数（D1） | ⚠️ **关注关系名单未采** |

**一句话结论**：`star 总数` 采了，**`star 的仓库列表` 没采**；`自建仓`只存了前 20 个的摘要；
`fork 仓`只知道数量、不知道 fork 了谁；`关注关系`只有计数、没有名单。

## 2. 完整数据模型（建议落盘结构）

```
account
├── _meta                          采集元信息
│   ├── login / user_id            id 是改名后仍可 join 的锚
│   ├── collected_at               采集时刻（CH 式数据必须记）
│   ├── spec_version               指标/字段版本
│   ├── tier                       minimal / rehearsal / full / deep
│   └── coverage                   每个块的完成度与缺失原因
│
├── identity                       身份锚（D1）
│   ├── id, node_id, login, type
│   ├── created_at                 注册时间 → 号龄
│   ├── updated_at                 实测≈最近触达，**不作档案编辑证据**
│   └── site_admin, user_view_type
│
├── profile                        档案（D1）
│   ├── name, company, blog, location, bio, twitter_username
│   ├── email_public(bool)         只落布尔
│   ├── hireable
│   ├── avatar: {type: identicon|photo, bytes, w, h, unique_colors, symmetry}
│   └── filled_count, shape        EMPTY/TEMPLATE/PARTIAL/RICH（派生）
│
├── counts                         规模（D1）
│   ├── public_repos               含 fork！不能当"自建仓数"
│   ├── public_gists
│   ├── followers, following
│   └── starred_total, watched_total
│
├── repos                          仓库（D8，建议全量保留采样到的）
│   ├── _agg: {total, sampled, coverage, own_n, fork_n,
│   │          own_empty, own_touched, own_committed,
│   │          fork_touched_n, first_created, last_push}
│   └── items[] (最多 N 个，按 pushed 降序)
│       ├── name, full_name, fork(bool), parent_full_name*
│       ├── size_kb, language, topics[], description
│       ├── created_at, pushed_at, own_push_after_create(bool)
│       ├── stars, forks, watchers, open_issues
│       ├── archived, disabled, default_branch, license, homepage, has_pages
│       └── own_commits_by_user (D9，仅抽查)
│
├── stars                          star 行为（D4 + D4L）
│   ├── total                      精确（Link 尾页，1 req）
│   ├── sampled_n, pages
│   ├── window: {first, last}      starred_at 的跨度
│   └── items[]: {repo_full_name, owner, starred_at, language, stars, topics}
│
├── watches                        订阅（D5，可选）
│   └── total + items[]: {repo_full_name, created_at}
│
├── events                         行为（D2，近 90 天 ≤300 条）
│   ├── total, by_type{}, dev_events, watch_events, push_events
│   ├── distinct_repos, first_at, last_at
│   └── by_day{} / by_hour{}       （可选聚合，做作息节律）
│
├── heat                           年度贡献日历（D13，0 API 配额，一次一年）
│   └── by_year{Y}: {status: ok|no_cells|unavailable,
│                    cells, span[2], active_days, total_contribs,
│                    max_streak, first_active, last_active,
│                    by_month{"YYYY-MM": n}}
│
├── orgs                           组织（D6）
│   └── items[]: {login, id, description, is_verified}
│
├── social                         关系（D10，可选）
│   ├── followers_total, following_total
│   └── samples[]: {login}         抽样 100 个，用于簇检测
│
└── derived                        派生指标（分析层算，不落原始）
    ├── P, SHAPE, NAMEMATCH, LOCFMT
    ├── OWN, OWNLIVE, OWNCMT, STARW, DEV, HEAT
    ├── AGE_AT_ACTION, IN_BURST, BATCH_SIZE
    ├── SINGLE_ACTION_YEAR（active_days ≤ 1）
    ├── ACTION_ALIGNED（last_active == fork 日 / 注册日）
    └── LOGIN_KIND(TS/PHONE/NUM/OTHER), TS_DECODE, TS_CLUSTER
```

\* `parent_full_name` 只在单仓端点有；列表端点拿不到（已实测）。

## 3. 每个块的采集成本与价值

| 块 | 端点 | 请求 | 价值 | 建议档位 |
|---|---|---:|---|---|
| identity + profile + counts | D1 | 1 | 基础，必采 | 所有档 |
| repos._agg | D8（3 页） | 1–3 | 判"有没有自己的仓" | `rehearsal`+ |
| **repos.items 全量** | 同上，只是别丢 | **0 额外** | fork 了谁、仓名语义、语言分布 | 同上 |
| stars.total | D4 `per_page=1` | 1 | star 消费宽度 | `rehearsal`+ |
| **stars.items** | D4L `per_page=100` | 1/100 条 | 品味画像、时间分布、**共星网络** | `full`+ |
| watches | D5 | 1/100 条 | 与 star 对比（只看不 star） | 可选 |
| events | D2 | 1–3 | 开发行为 vs 挂机 | `minimal`+ |
| orgs | D6 | 1 | 弱（95% 无 org） | `standard`+ |
| social.samples | D10 | 1/100 条 | 簇检测（批量号互关） | `deep` |
| own_commits | D9 | 1/仓 | "自己写代码"硬证据 | `deep` |

**成本不变、数据翻倍的三个改法**（当前就在白白丢弃）：

1. **D4 不要用 `per_page=1`**。改成 `per_page=100` 第一页 → 同样 1 个请求，白得 100 个 star 仓；
   精确总数用一次 `per_page=1` 的 Link 补（合计 2 req，但信息量差 100 倍）。
2. **D8 的 `own_details` 从 20 条放开**，并把 fork 仓的 `name/language/size/pushed` 也存下来——
   fork 了谁、fork 后有没有动，全部来自已经拿到的响应，**0 额外请求**。
3. **D3 的 `per_page=1` 同样浪费**：那一页本来就是一个完整 repo 对象，存下来就是"最近 push 的仓"。

## 4. 请求数与档位（重算后）

| 档位 | 组成 | 请求 | 覆盖的判据 |
|---|---|---:|---|
| `screen` | D1 | 1 | 档案形状、号龄、仓数 |
| `minimal` | D1+D2×1+D3+D4 | 4 | + 活跃、star 宽度 |
| `rehearsal` | D1+D4+D8×1 | **3** | + 自建/fork 结构（已验证可分开两组） |
| `standard` | rehearsal+D2+D6 | 5–6 | + 开发行为、组织 |
| `full` | standard+D8 全量+D4L×1+头像 | 6–9（+0 API 头像） | + star 清单、仓名语义 |
| `deep` | full+D9×3+D10 抽样+D5 | 10–14 | + 本人提交、关注簇、watch |

## 5. 字段 → 判据映射（不浪费任何一项）

| 字段 | 落到哪个判据 | 单独可信度 |
|---|---|---|
| `created_at` + 行为时间 | `AGE@action` | 弱（老号可买） |
| `profile.*` 填写情况 | `P` / `SHAPE` | 中（TEMPLATE 才有效） |
| `avatar.type` | 弱正向 | 很低 |
| `counts.public_repos` | **仅用于校验采样完整性**（`sampled == public_repos`） | — |
| `repos._agg.own_n` | `OWN`（有没有自己的仓） | 中强 |
| `repos._agg.own_touched` | `OWNLIVE` | 中 |
| `repos.items[].own_commits_by_user` | `OWNCMT`（硬证据） | 强 |
| `repos.items[].fork + name` | fork 了谁 / 仓名语义 | 中 |
| `stars.total` | `STARW` | 中（演练仅 11pp） |
| `stars.items[].starred_at` | star 节律、批次、共星网络 | 中强（新增） |
| `events.by_type` | `DEV` | 中 |
| `events.by_hour` | 作息节律 | 弱（AI 时代失效） |
| `orgs` | 弱正向 | 很低 |
| `social.samples` | 互关簇 | 中强（新增） |
| `login` 形态 | `TS/PHONE/NUM` | 强（但属批量性轴） |

---

## 6. 落地顺序（按"0 额外请求优先"）

1. **D8 保留全部采样仓 + fork 仓字段**（0 请求，直接提升"fork 了谁"能力）
2. **D4 改成 100/页 + 存 starred_at**（+1 请求/人，拿到 star 清单）
3. **D10 followers/following 抽样**（+1~2 请求/人，做互关簇）
4. **D9 抽查 3 个自建仓的本人提交**（+3 请求/人，硬证据）
5. **D5 watch 列表**（可选，区分"只看不 star"）

> 前三步做完，一个账户的记录就会从当前的 ~1.5 KB 变成 ~40 KB（含 100 star + 300 仓），
> 但**请求数只增加 1–2 个**。这就是"不要浪费数据"的具体含义。

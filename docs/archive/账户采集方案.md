# GitHub 账户信息采集方案（字段级指南）

> 目标：回答「**哪个端点、哪个字段、花几个请求、能拿到什么、能用来判什么**」。
> 适用对象：`/users/{login}` 及其附属端点 + `github.com/{login}` 页面 + 单个仓库端点。
> 前置：[`数据采集方案.md`](数据采集方案.md)（通道实测）、[`README.md`](README.md)（fork 地基与数据边界）
> 纪律：全部匿名只读；不登录；公开邮箱只落布尔；不采私有数据。

---

## 0. 配额与传输前提（决定方案形状）

| 事实 | 数值 | 对方案的影响 |
|---|---|---|
| 匿名 core 配额 | **60 次/小时/IP** | 8.2 万人 × 4 req = 不可行，必须代理分摊或抽样 |
| 认证 core 配额 | 5,000/小时/账号 | 本项目**不登录**，不采用 |
| Search 独立桶 | **10 次/分钟**（匿名） | `total_count` 类计数专用，不能用于逐人采集 |
| 二级限流 | ≈1 次/秒软约束 | 页间 sleep 0.8–1.2s |
| 条件请求 304 | **不计入配额**（官方文档口径，未实测） | 二次采集同一账号应带 `If-None-Match`；`etag` 落盘 |
| 资源分桶 | `X-RateLimit-Resource: core / search / graphql` | 判断这次请求走哪个桶 |

**传输**：本机对 `api.github.com` 有**按 TLS 指纹的选择性抑制**，`requests` 直连必死；
统一用 `curl_cffi` + `impersonate` 轮换（`chrome / firefox133 / safari17_0 / edge101`）。
`github.com` HTML 同一现象，但成功率随窗口波动（2026-11-05 实测两页均 200）。

## 1. 端点总表（14 个采集单元）

| ID | 端点 | 请求 | 一次拿到 | 用途 | 备注 |
|---|---|---:|---|---|---|
| **D1** | `GET /users/{login}` | 1 | 全部档案字段（见 §2） | 主表，一切的基础 | 404 = 删号/改名，本身是信号 |
| **D2** | `GET /users/{login}/events/public?per_page=100` | 1–3 | 近 90 天公开事件（≤300 条） | 开发行为 vs 挂机 | 上限 300 条/90 天；`/events` 含私有，**用 `/events/public`** |
| **D3** | `GET /users/{login}/repos?per_page=1&sort=pushed` | 1 | 仓库总数（Link 尾页）+ 最近 push 仓 | 计数 + 活跃度 | `per_page=1` 只为拿 Link 尾页 |
| **D4** | `GET /users/{login}/starred?per_page=1` | 1 | **star 总数**（Link 尾页） | star 消费宽度 | 加 `Accept: application/vnd.github.star+json` 可拿 `starred_at` |
| **D5** | `GET /users/{login}/subscriptions?per_page=1` | 1 | **watch 总数** | 与 star 宽度对比（只看不 star = 潜水） | 很少人用，判别力待测 |
| **D6** | `GET /users/{login}/orgs` | 1 | 组织列表 | 真人常挂 org | 实测 95% 无 org，判别力弱 |
| **D7** | `GET github.com/{login}`（HTML） | **0 API 配额** | 贡献日历 / 成就徽章 / profile README / pinned 仓 / "Joined" | **最强的"真实活动"证据** | 解析脆、会被抑制；与 API 结果分列，不互相冒充 |
| **D8** | `GET /users/{login}/repos?per_page=100&sort=pushed&page=N` | 1–3 | 仓库明细：`fork` 布尔 / size / created / pushed | **自建 vs fork 结构** | 关键：`public_repos` 含 fork，必须用 D8 才能看自建 |
| **D9** | `GET /repos/{owner}/{repo}/commits?author={login}&per_page=1` | 1/仓 | Link 尾页 = 本人在该仓的提交数 | **"自己写代码"的硬证据** | 只需抽查最近 3 个自建仓 |
| **D10** | `GET /users/{login}/followers|following?per_page=1` | 1+1 | 关系总数 | 社交宽度（D1 已含，通常不需要） | 省查 |
| **D11** | `GET /repos/{owner}/{repo}` | 1 | 单个 repo，含 `parent` / `source` | 确认 fork 来源与上游 | 列表端点**不含** `parent` |
| **D12** | `GET /search/commits?q=author:{login}` | 1 | 全站提交总数（`total_count`） | 跨仓生产能力（近似） | 10/min；**commits 搜索必须带关键词，不能裸 author** |
| **D13** | `GET github.com/users/{login}/contributions?from=Y-01-01&to=Y-12-31` | **0 API 配额** | **一整年**的逐日贡献（365 格 + 每日精确计数） | 年度活跃曲线、`SINGLE_ACTION_YEAR` | 一次一年、**不支持单月**；解析与实测见 §11 |
| **D14** | 头像 CDN `avatars.githubusercontent.com/u/{id}?v=4` | **0 API 配额** | 图片本体（先 HEAD 看大小） | 默认 identicon vs 上传照片 | 只能正向；阈值实测见 §4.5 |

> **D7 是唯一"不占 API 配额"的通道**，也是唯一能拿到贡献日历与成就的通道。
> 代价是 `github.com` 会被按目标抑制（TLS 层超时，而 `api.github.com` 同时正常）。

## 2. 字段级映射：`/users/{login}`（D1）

| 字段 | 类型 | 语义 | 怎么用 | 陷阱 |
|---|---|---|---|---|
| `id` | int | 用户唯一 ID，**改名不变** | **跨改名 join 的锚**：fork 名单按 login 对不上时，用 id 对 | 无法通过 API 反查旧 login |
| `login` | str | 当前登录名 | 主键（会变！见 id） | 改名后 fork 名单里是旧名 |
| `node_id` | str | GraphQL 用的 base64 ID | 无用（不登录 GraphQL） | — |
| `type` | str | `User` / `Organization` / `Bot` | 直接分流，bot/org 不进真人评分 | — |
| `user_view_type` | str | `public` / `private` | 少见，暂不用 | — |
| `site_admin` | bool | 是否 GitHub 员工 | 几乎恒 false | — |
| `name` | str? | 显示名 | **语义真实性**：像不像人名、与 login 有无对应 | 中文用户常用昵称/艺名 |
| `company` | str? | 公司 | 档案完整度 + 语义（`@org` 形式可对上 org） | 可随便填 |
| `blog` | str? | 主页 URL | 档案完整度；域名可判"个人站/公司站/空" | 常为空串 `""` 而非 null |
| `location` | str? | 地点 | **模板形判定**（"城市, 国家"格式）与地名真伪 | 可编造；离线地名库缺失 |
| `email` | str? | **公开**邮箱 | **只落布尔 `has_email`**（项目纪律） | 绝大多数为 null |
| `hireable` | bool? | 是否在找工作 | 弱正向 | 基本没人填 |
| `bio` | str? | 简介 | 档案完整度；模板味（破折号/竖线） | 可由 LLM 生成 |
| `twitter_username` | str? | X 用户名 | 档案完整度 | 常为空 |
| `public_repos` | int | **含 fork** 的公开仓数 | ⚠️ 对 forker 恒 ≥1 → **不能**用它判断"有没有自己的仓" | 必须用 D8 的 `fork` 布尔拆开 |
| `public_gists` | int | 公开 gist 数 | 内容产出（弱正向） | 少有人用 |
| `followers` | int | 粉丝数 | 弱正向（≥10 才有意义） | **0 粉方向是反的**（沉默开发者更多） |
| `following` | int | 关注数 | 弱正向 | 0/0 组合在爆发窗反而更少 |
| `created_at` | iso | 注册时间 | **号龄**；`行为时间 − created_at` = 年龄@行为 | 老号可以是买来的 |
| `updated_at` | iso | 档案最后更新 | ⚠️ **实测≈最近一次触达（登录/操作）**，不是档案编辑时间 | 语义不可靠，只做弱证据 |
| `avatar_url` | str | 头像 CDN 地址 | 拉图判 identicon（§4.5） | URL 形态对默认/上传都一样，**API 无法区分** |

## 3. 字段级映射：仓库列表（D8）

| 字段 | 用法 | 陷阱 |
|---|---|---|
| `fork` (bool) | **自建 vs fork 的分水岭** | — |
| `size` (KB) | `≤2` ≈ 空壳（`own_empty`） | 大仓可能是导入的模板 |
| `created_at` | 自建仓建仓时间 | — |

| `description` / `topics` | 内容真实度 | 可空 |
| `language` | 技术语言分布 | — |
| `archived` / `disabled` | 死仓 | — |
| `default_branch` | `main` / `master` / 其他 | 模板指纹（弱） |
| `parent` / `source` | **仅单仓端点有** | 列表端点没有，别指望 |

## 4. HTML 页面（D7）能拿到什么

| 区域 | 选择器线索 | 数据 | 用法 |
|---|---|---|---|
| 贡献日历 | `td[data-date][data-level]` | 过去一年逐日贡献等级 0–4 | **最强活动证据**：连续数月逐日节奏几乎无法伪造 |
| 成就徽章 | `img.achievement-badge[alt]` | Pull Shark / Quickdraw / YOLO / Starstruck / Arctic Code Vault… | 由真实行为授予；用户可在设置里隐藏 |
| Profile README | `article.markdown-body` | 自述正文 | 有 = 有自述意愿（强正向） |
| Pinned 仓 | `.pinned-item-list-item` | ≤6 个自选仓 | 精选展示 = 真人行为 |
| 组织 | `a[itemprop="worksFor"]` | 组织链接 | 与 D6 互证 |
| Joined | `Joined {date}` | 注册年月 | 与 `created_at` 互证 |
| 头像 | `img.avatar-user[src]` | 图片本体 | identicon 判定（§4.5） |
| Stars 页 | `?tab=stars` | star 列表 | 与 D4 总数互证 |
| 成就的可信度 | — | — | ⚠️ 可隐藏，**没有徽章 ≠ 假号** |

### 4.5 头像 identicon 判定（0 API 配额）

1. 用 `user_id` 拼 URL：`https://avatars.githubusercontent.com/u/{id}?v=4&s=460`（不需要额外 API 请求）
2. 先 **HEAD 看 `Content-Length`**（0 字节下载）：
   - `< 8 KB` → 判 `identicon`（实测默认头像 3.2–3.6 KB）
   - `> 20 KB` → 判 `photo`
   - 8–20 KB 的边界样本才下载解码
3. 解码后三指标任二命中即判 `identicon`：唯一色数 `<300`、前 3 色占比 `>60%`、左右镜像对称度 `>95%`
4. 实测（2026-11-05，8 个已知样本）：

| 类型 | 字节 | 尺寸 | 唯一色 | 前3色 | 对称度 |
|---|---:|---|---:|---:|---:|
| 默认 | 3 KB | **420²**（固定） | 53–110 | 75–82% | 99–100% |
| 上传 | 31–128 KB | 208²–460² | 3,138–3,881 | 0.6–11% | 0–12% |

5. ⚠️ 弱证据：老号也可能用默认头像；AI 生成头像很便宜。**「有自定义头像」才是正向**，「默认头像」不构成负向。

## 5. 采集档位（请求数/人）

| 档位 | 组合 | 请求 | 适用 |
|---|---|---:|---|
| `screen` | D1 | **1** | 全量筛查：`public_repos`、号龄、档案形状 |
| `rehearsal` | D1 + D4 + D8×1 | **3** | 已在 50 人演练中验证可分开两组，性价比最高 |
| `minimal` | D1 + D2×1 + D3 + D4 | **4** | 号龄 + 活跃 + 仓数 + star 宽度 |
| `standard` | minimal + D6 | 5–6 | + 组织 |
| `full` | standard + D8×3 | 6–9 | + 自建/fork 结构与空壳 |
| `deep`（已实现） | D1+D2×1+D3+D4+D4L×1+D6+D8×3 | **8** | + **star 了哪些仓**（D4L）、fork 明细 |
| `deep` + D9 | 再加 3 个自建仓的 `commits?author=` | 11–12 | + "自己的仓里有没有本人提交" |

**两段式**（推荐）：全量 `screen`（1 req）→ 只有 `public_repos==1` 等形态可疑者补到 `full`。
理由：`public_repos==1` 意味着"名下只有一个仓 = 这次 fork"，实测在真实 forker 里只占 1.9%。

## 7. 韧性设计与断点

| 机制 | 做法 |
|---|---|
| 指纹轮换 | `curl_cffi` 4 个 `impersonate` 档位，失败即换，每次换档新建 session |
| 抑制记账 | **按主机**记（`api.github.com` 与 `github.com` 互不影响） |
| 代理轮换 | 读业务响应自身的 `X-RateLimit-Remaining`，`≤3` 即换出口 |
| 断点 | 每档位独立 JSONL，`done = http ∈ {200,404}`；`http:0` 失败墓碑下轮重扫 |
| 页级重试 | 长跑采集器必须页级重试（一次失败不能报废整轮，2026-11-05 踩过） |
| 墓碑语义 | 404 = 永久（删号/改名），不重试；0 = 临时失败，重试 |
| 落盘纪律 | 当场落盘：CH 是衰减抽样，HTML 也会变 |

## 8. 采集状态集合（记录"哪些账号已经采完"）

实现：[`collect_state.py`](collect_state.py)。参照同机项目 `util/cache.py` 的集合接口，但按本项目纪律改造了两点：
**JSONL 是唯一事实来源**（Redis 只是索引，挂了能重建）、**异常不再静默吞掉**（连接失败会明确降级）。

### 8.1 三类终态，三个集合（不能合并）

| 集合 | 含义 | 后续动作 |
|---|---|---|
| `done` | 所有必需单元 200，且 D8 采样覆盖全部仓库 | 跳过 |
| `gone` | 404（删号/改名） | **永久跳过** |
| `partial` | 采到了但覆盖不全（如 300/1564 仓） | 跳过，等上限放开后重采 |

> 把 `partial` 混进 `done`，分析层就会把"没采到"当成"没有"——这正是 §6 审计里那个 `own=0` 假阴性的来源。

### 8.2 键设计

```
grf:v1:{集合名}:{档位}:done      SET
grf:v1:{集合名}:{档位}:gone      SET
grf:v1:{集合名}:{档位}:partial   SET
```

- 集合名默认取输出文件名词干（如 `profile_tier_rehearsal_rea_p98`），天然按仓库/批次隔离
- **档位必须进键**：同一个人采了 `minimal` 不等于采了 `full`
- **`kind` 必须进键**（踩过：漏掉它会让 done 与 gone 命中同一个 SET）
- 前缀 `grf:v1:` 与同机其它 Redis 项目隔离；升级 schema 换 `v2` 即可共存

### 8.3 写入顺序与重建

```
采集 → 写 JSONL → SADD 索引
```
先落盘再写索引：崩溃最坏情况是"索引少几条"，下次启动 `warm_from_jsonl()` 重建即可；
反过来（先 SADD 后落盘）会永久丢账号。

`warm_from_jsonl()` 是**幂等**的：先清空该集合的三个键，再从 JSONL 全量重算。
一个 8 万行的文件重建约 1–2 秒，所以每次启动顺手重建最省心。

### 8.4 降级

`backend="auto"`：Redis `ping()` 失败 → 自动切 SQLite（`data/state/collect_state.db`，
表 `collected(name, tier, login, kind, updated_at)`，主键三元组）。调用方 API 完全一致。

### 8.5 实测（2026-11-05）

| 集合 | done | partial | gone | 说明 |
|---|---:|---:|---:|---|
| `profile_tier_rehearsal_rea_p98` / rehearsal | 45 | 4 | 0 | 与 §6 审计的"45/49 完整、4 个采样不全"完全一致 |
| `profile_tier_full` / full | 110 | 0 | 6 | 6 个 404 墓碑 |

续采验证：49 人已完成 → 只重试 1 个 `http=0` 的账号（`aryan-singh-git`，两轮仍失败，**保持 pending 不写索引**，
下轮自动再试）。

2. 公开 email 只落布尔；不落原文

## 10. 分页、排序与增量（2026-11-06 实测补）

### 10.1 fork 名单的排序选项

| 参数 | 语义 | 用途 |
|---|---|---|
| `sort=oldest` | 按 fork 创建时间正序 | **全量补历史**：页码不漂移，配合 `.page` 游标断点续采 |
| `sort=newest`（默认） | 倒序 | **增量**：新 fork 在最前，翻到已知边界即停 |
| `sort=stargazers` / `watchers` | 按 **fork 仓**的 star/watch | 找"有影响力的 fork"，不适合全量 |

**没有 `since`/`until`**（只有 `sort`/`per_page`/`page`）——增量只能"翻到边界停"，不能查询时间区间。

```
增量算法：sort=newest 从第 1 页翻
  连续 50 个 fork_id 已在本地 → 停
  或 全页 created_at ≤ 水位 − 1h → 停（兜底，防水位/集合残缺时翻穿）
  水位 = 上次见到的最大 fork_created_at，存 .inc.json
对账：预期新增 = forks_count(本次) − forks_count(上次)；差额 = 期间被删除的 fork
```

成本：rea 新增 ~1,122/天 = 12 页 ≈ 12 分钟/天；全量 1,079 页 ≈ 18 小时。

### 10.2 三个必须修的分页缺陷（**2026-11-06 已全部修复**）

| 单元 | 缺陷 | 后果 | 状态 |
|---|---|---|---|
| D6 | `/orgs` **没传 `per_page`** → 默认 30 | >30 个组织被静默截断 | ✅ 已修：`?per_page=100` |
| D8 | 固定 3 页 = **最多 300 个仓** | 仓多的人 `own_count` 是采样值 | ✅ 已修：页数由 D1 的 `public_repos` 算（`ceil(total/100)`，上限 10 页/1000 仓），并回报 `repos_complete` |
| D8 | `own_details` 只存前 20 个自建仓 | 个人主页仓可能漏判 | ✅ 已修：新增 `has_profile_repo`（遍历全部采样仓比对 `name == login`，0 额外请求） |

**修复验证**（2026-11-06，真实账号）：

```
arwin-cc: pages_used=4  sampled=387  total_hint=387  complete=1  own=2  fork=385  主页仓=0
```

`public_repos=387` 自动算了 **4 页**（原实现只会采 300 个），并判定 `repos_complete=1`。

**实测审计**（openclaw 2,700 人 D1 池）：`public_repos > 300` 的占 **14.63%**（>500 的 9.04%，最大 38,708）。
storytold full 档 94 人里有 **6 人**采样不全，其中 **1 人**因此得到假的 `own_count=0`。

> **判据纪律**：`own_count == 0` 只有在 `repos_complete == 1`（即 `sampled_repos >= public_repos`）时才可下结论；
> 否则必须记 `unknown`。这条与"缺失 ≠ 0"是同一条红线。
>
> ⚠️ 已落盘的 **50 条 deep 记录是在修复前采的**，没有 `repos_complete` / `has_profile_repo` 字段——
> 需要一次 `--force` 重采（约 60 个请求）才能补齐。

### 10.3 Link 尾页的边界情况

## 11. 年度贡献日历（D13，0 API 配额）

```
GET https://github.com/users/{login}/contributions?from={Y}-01-01&to={Y}-12-31
```

### 11.1 粒度：**一次一年，不支持单月**

| 请求 | 实际返回跨度 |
|---|---|
| `from=2026-10-01&to=2026-10-31` | 2026-01-04 → 2026-12-26（365 格） |
| `from=2026-01-01&to=2026-12-31` | 同上，完全一致 |
| `from=2024-01-01&to=2026-12-31` | 仍是 365 格（一年），**不叠加** |
| 不带参数 | 2025-11-02 → 2026-10-31（滚动 12 个月） |

要多年 → 每年一次请求。要"fork 当月" → 取该年的日历再按月切片。

### 11.2 解析（正则，实测有效）

```html
<td data-date="2026-06-18" data-level="4" ...></td>
<tool-tip ...>1 contribution on June 18th.</tool-tip>
```

```python
CELL  = re.compile(r'data-date="([\d-]+)"[^>]*data-level="([0-4])"[^>]*></td>\s*'
                   r'<tool-tip[^>]*>(.*?)</tool-tip>', re.S)
COUNT = re.compile(r'(?:([\d,]+)|No)\s+contributions?\b')
```

产出：365 个 `(date, level, count)` → `active_days` / `total_contribs` / `max_streak` /
`first_active` / `last_active` / `by_month{}`。

## 12. watch 通道状态（2026-11-06 **终审**）

| 端点 | 方向 | 实测 | 判定 |
|---|---|---|---|
| `/repos/{o}/{r}/subscribers` | 仓→人 | **401 `Requires authentication`**（同一时刻配额剩 59，排除限流） | **已关闭** |
| `/users/{login}/subscriptions` | 人→仓 | **204 No Content、body 为空**——测了 3 个账号（steipete / 18534516725 / torvalds），配额都在 50 上下，全部 204 | **功能性关闭** |

**204 是最危险的形态**：它不是 401/403 那种一眼可见的拒绝，而是"成功但没有内容"。
任何解析器都会把它读成"这个人订阅了 0 个仓"——**这是伪造数据，不是缺失数据**。
所以采集层必须显式判断：

```python
if status == 204:
    return "unavailable"      # 绝不能落成 {"watched": []}
```

`subscribers_count` 始终可用（rea 1,652 / openclaw 1,694），但**只有计数、没有名单**。

> ⚠️ 方法学教训：判定通道死活**必须带对照请求**（本次用 `/users/{x}/starred` 作对照）。
> 第一版脚本把"网络失败(0)"当成"接口拒绝"，差点把"未知"写成"彻底不可得"；
> 第二版又差点把 204 当成"0 订阅"。判定矩阵：
> `0` = 未知；`204` = 无内容（不可用）；`401/403+rem>0/404` = 拒绝；`403+rem=0` = 配额问题。

# 数据结构设计

> 本文件讲清楚：数据以什么形状存储、为什么这样设计、有哪些已知问题。
> 对应代码：`scripts/collect/collect_core.py`（信封与九态）、`scripts/analysis/_compute_*.py`（特征表）。

---

## 一、三层结构（为什么要分三层）

```
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层：事实层（不可变）                                       │
│   data/raw/*.jsonl                                             │
│   一次采集一次追加，只增不改                                     │
│   ★ 唯一事实来源：丢了就要重采                                   │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层：索引层（可重建）                                       │
│   Redis / SQLite（本项目最终未使用）                             │
│   只记录"谁已完成"，丢了能从 JSONL warm 回来                      │
├──────────────────────────────────────────────────────────────┤
│ 第 3 层：产物层（可再生成）                                     │
│   data/out/features_*.csv   一人一行的特征表                     │
│   data/out/*.md             统计与对照                          │
│   figs/*.png                图                                  │
│   ★ 全部可由第 1 层离线重算，0 网络请求                          │
└──────────────────────────────────────────────────────────────┘
```

**设计理由**：采集是最贵的一步（9 天、1.87 GB、223 万条）。
只要第 1 层完整，第 3 层可以随时用不同口径重算 —— 本项目确实这么做了十几次。

## 二、第 1 层：统一信封（一个 schema 管 8 个维度）

```python
@dataclass
class Record:
    login: str              # 主键，串起所有维度
    dim: str                # "D1" / "D2B" / "D4L" / "D8H" / "D9" / "D13" / "D14" / "D15"
    outcome: str            # 九种状态之一（见第三节）
    http: Optional[int]     # 原始状态码；None = 没拿到响应
    ts: float               # 采集时刻（Unix）
    attempt: int            # 第几次尝试
    payload: dict           # 维度专属数据
    note: str               # 人读原因："账号不存在" / "空仓库"
```

**落盘样例**（一行一个 JSON，无缩进省体积）：

```json
{"login":"sam***","dim":"D1","outcome":"OK","http":200,"ts":1794634042.88,"attempt":1,
 "payload":{"user_id":20317701,"created_at":"2016-07-06T10:00:18Z","public_repos":15,
            "followers":2,"following":1,"type":"User"},"note":""}
```

### 为什么用"信封 + payload"而不是"每维度一套字段"

| 旧设计（本项目早期） | 新设计 |
|---|---|
| D1 用嵌套 `d1: {...}` | 统一 `payload: {...}` |
| D13 用 `status: "ok"/"unavailable"/"gone"` | 统一 `outcome` |
| D14 用 `status: 200(int) + type` | 统一 `outcome` |
| 聚合代码要为每个维度写特例 | **只读 `outcome` + `payload`** |

**旧设计有 3 种状态表示法，导致兼容层必须写 6 个分支。**

## 三、九态设计（本项目最贵的教训）

### 3.1 为什么不能用 `http=0`

旧代码用 `http=0` 同时表示三件事：

| 真实含义 | 旧表示 | 后果 |
|---|---|---|
| 网络失败（该重试） | `http=0` | 无法区分 |
| 所有子资源 404（不该重试） | `http=0` | 每次重跑都白跑 |
| 解析失败（该重试） | `http=0` | 被当成"没数据"写进特征表 |

### 3.2 九态定义

| Outcome | 触发条件 | 终态 | payload | 进特征表 |
|---|---|:---:|---|:---:|
| `OK` | 200 且有内容 | ✅ | 数据 | ✅ |
| `EMPTY` | 资源存在但为空（0 仓/0 提交/409 空仓） | ✅ | **值 0** | ✅ |
| `DELETED` | **账号** 404（注销/封禁/改名） | ✅ | `None` | ❌ |
| `NOT_FOUND` | **子资源** 404（仓库已删/改名） | ✅ | `None` | ❌ |
| `PRIVATE` | 403 非限流 | ✅ | `None` | ❌ |
| `AUTH` | 401 | ✅ | `None` | ❌ |
| `RATE_LIMIT` | 403/429 + 配额 | ❌ 重试 | — | ❌ |
| `NETWORK` | 连接失败/超时/5xx | ❌ 重试 | — | ❌ |
| `BAD_RESPONSE` | 200 但解析失败 | ❌ 重试 | — | ❌ |

**两条硬规则**：

1. **终态只采一次**（记墓碑），重跑直接跳过 → 省下大量重复请求
2. **`EMPTY` 是 0，`DELETED` 是 `None`** → 混成同一个 0 会让"零提交率"彻底失真

**验证**：`_test_error_handling.py` 47 项测试中，九态映射 16/16 通过。

## 四、文件命名与映射（唯一权威）

```python
# collect_core.py
DIMS = {
    "D1":  DimSpec(..., "profile_tier_screen_{tag}_all.jsonl"),
    "D2":  DimSpec(..., "atom_{tag}.jsonl"),
    "D2B": DimSpec(..., "events90_{tag}.jsonl"),
    "D4L": DimSpec(..., "starlist_{tag}.jsonl"),
    "D8H": DimSpec(..., "repos_html_{tag}.jsonl"),
    "D9":  DimSpec(..., "commits_{tag}.jsonl"),
    "D13": DimSpec(..., "heat_{tag}_all.jsonl"),
    "D14": DimSpec(..., "avatar_{tag}.jsonl"),
    "D15": DimSpec(..., "profile_html_{tag}.jsonl"),
    "D6":  DimSpec(..., "orgs_{tag}.jsonl"),
}

def dim_path(dim, tag, out_dir="data/raw"):
    return os.path.join(out_dir, DIMS[dim].file_pattern.format(tag=tag))
```

**纪律：其他任何地方不许硬编码文件名** —— 一律走 `dim_path()`。

> 这条纪律是**吃过亏才立的**：`_data_volume.py` 曾假设文件名是 `{dim}_{tag}.jsonl`，
> 结果 rea/openclaw 的列表数据被判为"缺失"（实际有 322 万条）。

## 五、两种列表数据的特殊结构

### 5.1 star 明细（`starred_all_{tag}.jsonl`）

```json
{"login":"kes***","outcome":"OK","n_pages":20,"n_items":2000,
 "complete":false,"truncated":true,"starred_total_est":10700,
 "items":[
   {"full_name":"666ghj/MiroFish","at":"2026-01-05T00:09:05Z","stars":85544,"lang":"Python","fork":false},
   {"full_name":"juanboy/MiroFish","at":"2026-01-05T00:08:58Z","stars":1,"lang":null,"fork":true}
 ]}
```

**关键字段**：

| 字段 | 含义 |
|---|---|
| `complete` | 是否拉完了全部页 |
| `truncated` | 是否触及上限（2,000 条） |
| `starred_total_est` | **真实总数**（从 Link 头读，截断时也能知道原量） |

**为什么上限是 2,000**：实测 p99 = 1,718，2,000 能保留 **94%** 数据，只多花 **4.6%** 请求。

### 5.2 repo 明细（`repos_all_{tag}.jsonl`）

```json
{"login":"kes***","outcome":"OK","n_pages":1,"n_items":66,
 "own_count":43,"fork_count":23,"complete":true,
 "items":[{"name":"t3code","full_name":"kes***/t3code","fork":true,"lang":null,
           "size_kb":1234,"stars":0,"forks":0,"created_at":"...","pushed_at":"..."}]}
```

**`own_count` / `fork_count` 是服务端提供的权威计数**，不依赖 `items` 长度。

## 六、第 3 层：特征表（一人一行）

### 6.1 结构

```csv
login,fork_ts,fork_age_days,fork_touched,acct_age_days,followers,followers_zero,
has_own,own_count,commit_total,commit_zero,avatar_photo,dev_event_ratio,...
sam***,1791...,30.6,0,2028.9,1,1,1,2,6,0,1,0.00,...
```

| 列组 | 示例字段 | 来源 |
|---|---|---|
| 时间轴 | `fork_ts` `fork_age_days` `fork_touched` | fork 名单（0 请求） |
| 档案 | `acct_age_days` `filled_n` `followers` `shape` | D1 |
| 仓库 | `own_count` `fork_count` `own_langs_n` | D8H |
| 提交 | `commit_total` `commit_zero` | D9 |
| 活跃 | `active_days` `dev_event_ratio` | D13 / D2B |
| 头像 | `avatar_type` `avatar_photo` | D14 |
| 成就 | `has_pull_shark` `has_collab` | D15 |

### 6.2 三条建表纪律

| 纪律 | 原因 |
|---|---|
| **列取所有行的并集** | 曾按第一行建表，导致 openclaw 整列丢失（`star_fork_delay_h`） |
| **缺失留 `None`，不填 0** | 否则"没采到"会被算成"确实是 0" |
| **布尔量统一转 1/0** | CSV 里写 `True`/`False` 会让比率算成 0（踩过） |

## 七、已知的设计问题（如实记录）

| # | 问题 | 影响 | 状态 |
|--:|---|---|---|
| 1 | **同一账号可能有多条记录** | rea D1 有 30,514 条重复（22%） | 聚合时按 login 去重 |
| 2 | **旧格式与新格式并存** | rea/openclaw 是旧格式，其余是新格式 | `legacy_to_outcome` 兼容 |
| 3 | **`own_details` 只存前 12 个仓** | 18–23% 的账号详情被截 | 计数不受影响 |
| 4 | **D9 的 `per_repo` 只存检查过的仓** | 未检查的仓无记录 | 设计如此 |
| 5 | **缺 schema 版本号** | 未来改结构无法识别旧数据 | ⚠️ 建议加 `schema_v` 字段 |

### 建议的改进（未实施）

```python
# 在信封里加版本号
{"schema_v": 2, "login": ..., ...}
```

这样未来改结构时，读取代码可以按版本分支，而不是靠猜字段。

## 八、一句话总结

> **第 1 层（JSONL）是不可变的真相，第 3 层（CSV/MD/PNG）是可重算的视图。**
>
> **九态是这套设计的核心**：它把"确实没有"（`EMPTY`，值 0）与
> "没采到"（`NETWORK`）彻底分开 —— 这是本项目最贵的一课。

## 九、缺陷修复记录（2026-11-15）

采集过程中暴露并修复的 5 个真实缺陷：

| # | 缺陷 | 后果 | 修复 |
|--:|---|---|---|
| 1 | **D14 依赖 D1 成功** | D1 失败 → D14 直接 BAD_RESPONSE，每仓丢 640–810 条 | 缺 user_id 时自己补一次 `/users` 请求 |
| 2 | **`--dims` 静默排除维度** | 漏写 D13/D15 时无任何提示 → 4 个仓完全没采 | 打印 `⚠️ 未采集 N 个维度 → D1, D2, ...` |
| 3 | **451 法律限制被当可重试** | 每次重试都失败，白烧 4 次请求 | 归入 `PRIVATE`（终态） |
| 4 | **3xx 归为 BAD_RESPONSE** | 仓改名/删除会反复重试 | 归入 `NOT_FOUND`（终态） |
| 5 | **D9 对 D8H 失败处理过粗** | D8H 网络抖动 → D9 整条作废 | 只有「人不存在」才终态，网络类失败明确标 `NETWORK` |

**验证**：`scripts/collect/_test_error_handling.py` **47 项全部通过**。

### 未能修复的一条（设计层）

| 缺陷 | 说明 |
|---|---|
| **D9 的 p² 损耗** | 「每人 2 个仓都成功」才算，导致覆盖率上限约 75–80%。**只能靠多轮补采**，无法从代码层消除（除非改成"部分成功也记"，但那会让 `commit_total` 含义变模糊） |

### 这条缺陷的真实代价

| 影响 | 数值 |
|---|---|
| ollama D9 从 45% 补到 90% 后 | 零提交率 **49.5% → 38.9%** |
| `commit_zero` 判据间距 | **3.9pp → 12.4pp** |
| 结论 | 从"判据失效"翻成"零重叠" |

> **数据不完整制造的是"判据失效"的假象，不是随机噪声。**

## 十、两种落盘格式（2026-11-18 新增）

项目里现在有**两种**原始数据格式，用途不同：

| 格式 | 文件 | 一行是什么 | 适合 |
|---|---|---|---|
| **分维度** | `profile_tier_screen_*.jsonl`、`repos_html_*.jsonl` …（9 个文件） | 一个人在某一个维度的结果 | 大规模分维度补采、按维度重试 |
| **一人一条** | `accounts_full_{tag}.jsonl` | **一个人的全部维度** | 拿"完整档案"、做个体分析 |

### 10.1 一人一条的结构

```json
{
  "login": "0x7***",
  "ts": 1794935705,
  "elapsed": 13.92,
  "outcomes": {"D1":"OK","D2B":"OK","D4L":"OK","D8H":"OK",
               "D9":"EMPTY","D14":"NETWORK","D6":"EMPTY","D15":"OK"},
  "dims": {
    "D1":  {"user_id":..., "created_at":..., "followers":...},
    "D8H": {"own_count":..., "own_details":[...]},
    "D9":  {"commit_total":..., "per_repo":[...]},
    "D15": {"achievements":[...], "has_pull_shark":..., "has_collab":...}
  },
  "_notes": {"D15": "..."}
}
```

### 10.2 三种生成方式

| 方式 | 命令 | 适用 |
|---|---|---|
| **新采集** | `collect_full.py --repo owner/repo --sample 2000` | 从未采过的仓库 |
| **合并旧数据** | `_combine_dims.py --tag frp` | 已有分维度数据，避免重采 |
| **多轮修复** | `_repair_loop.py --target 0.85` | 单轮完整率不够时补齐 |

### 10.3 完整率与修复收敛

单次请求成功率实测在 20%–85% 之间剧烈波动。
7 个 API 维全成功的概率 = 0.85⁷ ≈ **26%**。

`collect_full.py` 的设计：
- 每个维度最多重试 3 次
- **失败维度再跑 2 轮**（换隧道窗口）
- 这样单账号完整率可达 **80–100%**

实测收敛：

| 仓库 | 首轮 | 修复后 |
|---|---:|---:|
| agency-agents | 18.4% | **92.8%** |
| frp | 62.1% | **76.4%** |
| nodejs-argo | 56.3% | **71.7%** |

### 10.5 读取时的重要约定

**同一账号可能有多条记录**（多轮修复产生）。读取时必须：

```python
# ✅ 逐维度取最优（不能只挑"维度最多的一条"）
recs = best_records("accounts_full_xxx.jsonl")
# 内部按 PRI = {OK:5, EMPTY:4, 终态:3, 可重试:1} 对每个维度单独择优
```

> ⚠️ **不能只挑"维度数最多的记录"** ——
> 单维补采（如 `--dims D15`）产生的记录只含 1 个维度，会被整个丢掉。
> 这个 bug 曾让 frp 的 Pull Shark 从 23.9% 误报成 41.7%。

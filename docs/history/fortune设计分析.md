# `aegiswizard/fortune` 设计分析

> 对照物：本项目（九维度全量 + 对照仓 + 时间控制）。
> 源码：`fortune/scanner.py`（333 行）、`fortune/heuristics.py`（约 170 行）。
> 本文只做**设计与方法学**评述，不评价作者意图。

---

## 一、它的定位：**仓库主自查工具**

从代码结构看，它服务的是这个场景：

> "我是仓库作者，我怀疑我的 star 里有买的，帮我看看。"

**四个证据**：

| 证据 | 说明 |
|---|---|
| 输入端只接受一个仓库 URL | 不做跨仓库、不做对照 |
| 输出是"这次扫描里哪些账号可疑" | 面向作者自己清理 |
| README 强调"免费、无需 token 也能跑" | 面向个人开发者 |
| 只统计聚合比例，不产出可审计的原始数据集 | 一次性的健康检查 |

**它不是**审计工具、不是取证工具、不是学术测量工具。
理解这一点，后面所有设计取舍都能解释。

---

## 二、架构：四步流水线

```
Step 1  取仓库元信息          GET /repos/{o}/{r}                 1 请求
        ↓ 读 stargazers_count 得到"总星数"
Step 2  翻 stargazer 名单     GET /repos/{o}/{r}/stargazers      ⌈N/100⌉ 请求
        ↓ Accept: star+json → 每条含 starred_at
Step 3  逐个取用户档案        GET /users/{login}                 N 请求
        ↓ 每人 1 请求，0.05s 间隔
Step 4  打分 + 外推           heuristics.score_user  →  rate × total_stars
```

**成本模型**（N = 抽样人数）：

| N | 请求数 | 有 token（5000/h） | 无 token（60/h） |
|---:|---:|---:|---:|
| 1,000（默认） | ~1,011 | **12 分钟** | **17 小时** |
| 5,000 | ~5,051 | 1 小时 | 3.5 天 |
| 全量 43 万 | ~434,000 | 87 小时 | 不可能 |

**设计上的合理处**：默认抽样 1,000——在"免费额度"和"够用"之间取了平衡点。

---

## 三、九条启发式（含权重）

判定线：**累计 ≥ 50 分即判"可疑"**，分数封顶 100。

| # | 规则 | 加分 | 作者的理由 |
|--:|---|---:|---|
| **1** | **账号创建**与**点星**同一天 | **+40** | 作者注释："single strongest signal，多数廉价机器人" |
| 2 | 零粉丝 / 极少粉丝 | +15 / +7 | "真开发者总会积累几个粉丝" |
| 3 | 不关注任何人 / 极少 | +10 / +5 | "机器人不关注人" |
| 4 | 无公开仓库 / 极少 | +15 / +7 | "真开发者会推代码" |
| 5 | 档案全空 / ≥4 项空 | +10 / +5 | "机器人不填 bio" |
| 6 | 创建后从未更新 | 少量 | "账号建完就不管了" |
| 7 | star 时账号很新（非同日） | 少量 | 新号突击点星 |
| 8 | 登录名形态可疑（≥5 位数字 / 长随机小写） | 少量 | "机器人常用 word+number" |
| 9 | **幽灵组合**（0 粉 ∧ 0 关注 ∧ 0 仓 ∧ 0 gist ∧ 全空档案） | 加成 | 多个零同时出现 |

**外加一条代码里写死的规则**：`/users/{login}` 返回 404 → **直接 score = 100，判可疑**。

## 四、四个关键设计问题（按严重程度）

### 问题 1（致命）：它假设 stargazer 名单公开可读

代码第 135–137 行：

```python
url = f"{GITHUB_API}/repos/{owner}/{repo}/stargazers"
resp = _get(url, _star_headers(token), params={"per_page": per_page, "page": page})
resp.raise_for_status()
```

第 137 行的 `raise_for_status()` 意味着：**只要不是 2xx 就直接抛异常**。

而本项目实测（2026-11-14，用一个有效的 5000/h token）：

| 请求 | 结果 |
|---|---|
| `/repos/torvalds/linux` | ✅ 200 |
| `/user/starred`（自己的） | ✅ 200 |
| **`/repos/torvalds/linux/stargazers`** | ❌ **404** |

**所以这个工具在"别人的仓库"上会直接抛 `HTTPError: 404 Client Error` 崩掉**，
而且错误信息不会告诉用户"你需要所有权"。

**它能工作的唯一场景：你分析的仓库是你自己（或有 admin 权限）的。**
这恰好与"仓库主自查工具"的定位吻合——**但 README 没把这个前提写清楚**，
读者会以为它能审任意公开仓库。

### 问题 2（严重）：抽样不是随机，却外推到全体

```python
estimated_total_fake = round(fake_rate * total_stars)   # 第 281 行
```

`_fetch_stargazer_pages` 从 **page=1** 开始翻，取前 `sample_size` 个。
GitHub 的 stargazers 默认按**点星时间升序**返回，所以"前 1000 个"是**最早的那批支持者**。

对 43 万星的仓库，最早 1000 人 ≈ 2020 年的早期用户；
最近 43 万人 ≈ 2026 年的爆发用户。**两者画像可以完全不同。**

**这正是本项目踩过的坑**：早期用单页抽样算出 rea 的"时间戳登录名"占 36%，
全量真值只有 **0.56%**——**放大了 64 倍**。

> 抽样可以，但必须**随机抽样**（或分层抽样），且**不能外推到全体**。
> 代码里那句"Results are extrapolated to the full star count"是设计缺陷。

### 问题 3（严重）：没有对照组，用绝对阈值判"假"

`score_user` 只输入一个人的档案与点星日期，**没有"正常用户长什么样"的基线**。

而本项目的实测显示：这些"低活跃账号特征"在**真实 forker 群体里同样高频**——

| 启发式 | 加分 | 对照组实测（真实 forker） |
|---|---:|---|
| 零粉丝 | +15 | rea **41.6%** / openclaw 28.1% |
| 无公开仓库 | +15 | 27% 没有自建仓 |
| 档案全空 | +10 | rea **45.4%** / openclaw 44.4% |
| 不关注任何人 | +10 | 36.8% / 32.5% |

**一个真实的"沉默开发者"**：账号两年、零粉丝、没建仓、档案没填 →
`0 + 15 + 15 + 10 + 10 = 50` → **正好被判"可疑"**。

这不是极端假设：本项目数据显示 **45% 的真实 forker 档案是全空的**。
**假阳性率会非常高。**

### 问题 4（中等）：删号 = 100 分

```python
if user_detail is None:
    score = 100, reasons = ["Account has been deleted or does not exist"]
```

注销账号的正常用户（换工作、隐私考虑、不再用 GitHub）与"刷完就删的小号"
在这个判据下**完全无法区分**。

本项目实测：rea 的 forker 里 404 占 **0.3%**，openclaw **1.0%**。
这个比例更像"正常流失"，而不是"批量蒸发的异常增长号"。

## 五、它做对的四件事

| # | 设计 | 为什么对 |
|---|---|---|
| 1 | **只用 REST API，不爬 HTML** | 合规、稳定、字段结构化 |
| 2 | **有速率限制处理**（403/429 → 等 reset） | 代码第 68–97 行，`_check_rate_limit` 会真的睡眠等重置 |
| 3 | **礼貌节流**（每人 0.05s） | 不打死服务端 |
| 4 | **保留 `starred_at` 时间戳** | 这是最有价值的设计——**有时间才能做时序分析** |

第 4 点尤其重要：`Accept: application/vnd.github.star+json`
能拿到每个人**点星的具体时刻**，这支撑了本项目第二强的判据
（`≤5 分钟 star+fork` 差 19.1pp）。

**它还做了一件对的事**：把每条判定理由写进 `reasons` 列表，而不是只给一个分数。
这让结果**可解释、可复核**——比黑箱评分好得多。

## 六、与本项目的方法对比

| 维度 | fortune | 本项目 |
|---|---|---|
| **目标** | 仓库主自查 | 方法学研究 |
| **身份来源** | star 名单（需所有者） | **fork 名单（可匿名）** |
| **覆盖** | 抽样 1,000 | **全量 252,662** |
| **对照** | ❌ 无 | ✅ 两个仓库互相对照 + 仓库内部对照 |
| **时间控制** | ❌ 无 | ✅ fork 龄分桶 |
| **判据** | 9 条绝对阈值 | 12 条**带效应量**的判据 + 21 条被证伪的 |
| **输出** | 一个"假星比例" | 分布、效应量、置信边界 |
| **结论** | "你的星里有 X% 是非真实的" | "**没有找到造假证据**" |

**最根本的差异**：

> fortune 给**一个数字**（假星比例），本项目给**一个边界**（公开数据能证明什么、不能证明什么）。

前者更容易传播，后者更接近事实。

## 七、怎么正确使用它

如果你要用这个工具，三条建议：

| 建议 | 理由 |
|---|---|
| **只对自己的仓库用** | 非所有者会在 `/stargazers` 拿到 404，直接崩 |
| **忽略"estimated_total_fake"，只看逐条 `reasons`** | 外推有抽样偏差（问题 2） |
| **把判定当"线索"而不是"结论"** | 绝对阈值假阳性高（问题 3） |

**最有价值的用法**：把 `starred_at` 拉出来画时间分布。
如果 10 万个星里有 6 万个挤在 3 小时内——那不需要任何启发式，看图就够了。
这正是本项目对 rea 得到的第一个强结论。

---

## 八、一句话总结

> **它是一个"面向仓库主的自查小工具"，不是一个"可审计的测量仪器"。**
>
> 它的九条启发式**方向对、阈值糙**；
> 它的抽样**省请求、但有偏**；
> 它最大的价值不是那个"假星比例"，而是**保留了 `starred_at`**——
> 有时间戳，才能做真正有说服力的时序分析。

**与本项目的关系**：它验证了"用 API + 时间戳看 star 行为"这条路可行；
本项目则证明了另一件事——**即使把维度做到九个、数据做到 223 万条，
用公开数据依然无法证明"造假"。**

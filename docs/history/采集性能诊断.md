# 采集性能诊断：为什么「一次采完一个人」只有 13 人/分钟

> 2026-11-14 · BettaFish 实测（7,688 人）
> 结论：**不是带宽不够，是方案在四个层次上都有浪费。**

---

## 一、问题陈述

「一次性采集完一个账户的全部信息」（`per_account`）实测 **13 人/分钟**，
7,688 人要 **9 小时**。而带宽物理下限只有 **2.3 小时**。

**利用率 25%。** 差距不是网络，是设计。

---

## 二、四层诊断（从表到里）

### 第 1 层：调度 —— 串行化把单点失败放大成整人失败

`per_account` 的循环是：

```python
for dim in 7 个维度:        # 串行
    rec = fetch(dim, login) # 一个维度失败 = 4 次重试 × 12s = 48s
```

**一个账号的总耗时 = 7 个维度耗时之和**，而其中任一维度超时就会拖住整个账号。

实测单个账号分解（同一时刻、同一隧道）：

| 维度 | 耗时 | 结果 |
|---|---:|---|
| D1 档案 | 1.2s | OK |
| D15 主页 | 1.8s | OK |
| D8H 仓库 | 14.1s | OK |
| D9 提交 | 29.0s | OK |
| D13 日历 | **20.2s** | **NETWORK** |
| D14 头像 | 5.3s | OK |
| D2 事件 | 2.8s | OK |
| D4L star | 1.4s | OK |
| **合计** | **~76s** | |

**76 秒里，42 秒（55%）花在失败与重试上。**

→ **修正 1：改用 `per_dim`**（一维采完再下一维），让同一维度的请求同质化，
失败不会跨维度传染，且可以让 32 个 worker 全部服务于同一个通道。

### 第 2 层：通道 —— HTML 在隧道上的硬失败率 45%

同一并发（32）、只改超时，成功率**不随超时上升**：

| 超时 | 成功率 | p95 | 吞吐 |
|---:|---:|---:|---:|
| 12s | 55% | 12.0s | 91 页/分钟 |
| 25s | 50% | 25.0s | 63 页/分钟 |
| 40s | 50% | 30.8s | 49 页/分钟 |

**p95 恰好等于超时值** —— 说明失败不是"慢"，是**连接挂住直到超时**。

→ **修正 2：超时调短（10s）+ 重试加多（5 次）**，
因为"快速失败再试"比"长时间等待"更划算。

### 第 3 层：体积 —— 选错了端点，浪费 3.6~143 倍流量

同一份信息，API 与 HTML 的体积差一个数量级：

| 信息 | HTML 方式 | API 方式 | 倍数 |
|---|---|---:|---:|
| 账户档案 | 主页 171 KB | `/users/{l}` **1.2 KB** | **143×** |
| 仓库清单 | `?tab=repositories` 223 KB | `/users/{l}/repos` **62 KB** | **3.6×** |
| 事件流 | `.atom` ~30 KB | `/events/public` 58 KB | HTML 更小 |
| 全年贡献 | `/contributions` 234 KB | **无 API** | 必须 HTML |

**原方案用了 3 个 HTML 页面（171+223+234 = 628 KB/人）**，
其中 **394 KB（63%）是可以用 API 以 63 KB 拿到的**。

→ **修正 3：D15 的字段用 API `/users` 拿，D8H 改用 API `/repos`。**
只有 **D13（贡献日历）没有 API 替代**，必须保留 HTML。

### 第 4 层：并发 —— 32 并发下 HTML 页面 100% 失败

这是最反直觉的一条。同一并发、同一超时（10s），端点类型决定生死：

| 端点 | 体积 | 32 并发成功率 | 吞吐 |
|---|---:|---:|---:|
| API `/users` | **1.2 KB** | **100%** | **292 请求/分钟** |
| API `/repos` | 62 KB | 84% | 161 请求/分钟 |
| **HTML 仓库页** | 223 KB | **0%** | **0** |
| **HTML 主页** | 171 KB | **0%** | **0** |

**算术原因**：32 并发 × 220 KB = **7.0 MB**，
而 5 Mbps 在 10 秒内只能传 **6.25 MB** → 队列全部超时 → **成功率 0%**。

而 1.2 KB 的 API 请求：32 × 1.2 KB = 38 KB，10 秒绰绰有余 → 100%。

→ **修正 4：按传输体积分池，而不是按账号分池。**
小响应走高并发（32–64），大响应走低并发（6–8）。

---

## 三、并发-吞吐曲线（实测）

**HTML 页面（223 KB）**：

| 并发 | 吞吐 | 带宽 |
|---:|---:|---:|
| 2 | 3.3 页/分钟 | 0.1 Mbps |
| 4 | 6.4 | 0.2 Mbps |
| 8 | 13.0 | 0.4 Mbps |
| 16 | 51.5 | 1.5 Mbps |
| **32** | **99.3** | **2.9 Mbps** |

**注意**：低并发时吞吐极低（固定握手开销占比大），
高并发时带宽利用率才上来——但**只对"能塞进带宽窗口"的页面成立**。
223 KB 的页面在 32 并发下刚好崩掉，说明 32 已接近这批页面的上限。

**API 小响应**：16 并发 → 201 请求/分钟；32 并发 → 292 请求/分钟，仍线性。

---

## 四、修正后的方案：双池并行

```
池 A（API，小响应）    并发 32   D1 D8H D4L D9 D14 D2
池 B（HTML，大响应）   并发 6    D13 D15
          ↓ 同一条隧道，互不阻塞
        按维度独立推进，失败不跨维度传染
```

**预期收益**：

| 项 | 原方案 | 新方案 | 倍数 |
|---|---:|---:|---:|
| 每人传输 | 660 KB | **405 KB** | 1.6× |
| 调度利用率 | 25% | ~70% | 2.8× |
| **实测速率** | **13 人/分钟** | **33 人/分钟** | **2.5×** |
| **ETA（7,688 人）** | **9 小时** | **~3.4 小时** | |

**剩下的 3.4 小时里，约 72 分钟是 D13 贡献页的纯带宽成本**（2.7 GB ÷ 5 Mbps），
这部分**无法用代码优化**——除非放弃 365 天日历，或换更宽的通道。

## 五、五条可复用的经验

| # | 经验 | 触发条件 |
|--:|---|---|
| 1 | **按响应体积分池，不按账号分池** | 同一批任务里响应体积差 10 倍以上 |
| 2 | **并发上限 ≈ 带宽窗口 ÷ 单响应体积** | 有固定带宽的代理链路 |
| 3 | **短超时 + 多重试 > 长超时** | 失败模式是"挂住"而非"慢" |
| 4 | **优先找 API 替代 HTML** | 需要从页面里抠 3–5 个数字时 |
| 5 | **成功率不随超时上升 = 硬失败，别再加时间** | 调超时无效时 |

## 六、附：一个被证伪的猜测

**猜测**："隧道限并发连接数，所以 32 并发没用。"
**实测**：32 并发确实达到 99 页/分钟（16 并发只有 51），**并发是有效的**。
真正的限制是**带宽 × 响应体积**，不是连接数。
